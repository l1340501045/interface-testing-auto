# 接口自动化测试与巡检平台

用于管理接口用例、配置执行环境、串联业务场景，并按计划执行巡检和查看失败结果。

当前可用范围是单接口用例的闭环：编辑请求与断言、导入 cURL 命令文本、发布为版本、提交执行、
由独立执行进程真实发起请求并回填结果，以及在页面上维护项目普通变量、执行环境、执行池目标
白名单和人工凭证。请求里的 `{{变量}}` 由项目／环境普通变量在发送前解析；未定义的变量在发出
请求前直接失败，不做静默替换，也不会把 `{{...}}` 当字面量发出去。

cURL 导入只解析命令文本、不访问目标：重复的查询参数与请求头、JSON 原文（含超出双精度范围
的长整数）按原样填进编辑器，无法保证等价导入的命令会被拒绝并列出原因。

规划能力还包括场景／运行／步骤范围的变量传递与响应提取、浏览器请求录制及巡检告警。

## 一、准备开发环境

需要 Docker Desktop、Docker Compose 和 Python 3。Python 只用于生成本机配置，
业务运行时与依赖全部在容器内。

```bash
make dev
```

首次运行会生成仅本机使用的 `.env`：随机生成数据库口令与加密主密钥，并选择可用端口。
已有 `.env` 与已有主密钥不会被覆盖。控制台会打印前端和后端地址，默认分别是
`http://127.0.0.1:15173` 与 `http://127.0.0.1:18080/health`。

`make dev` 会持续运行 Compose Watch，源码热更新仍然有效。只想把容器跑起来时用
`make up`，此时依赖变更不会自动重建。停止用 `make stop`，数据库卷会保留。

数据库角色初始化与迁移由管理 API 在启动时自动完成（`apps/api/entrypoint.sh`），
不需要手工执行迁移命令。

## 二、创建首位管理员

```bash
make admin
```

按提示输入登录名、显示名与密码（至少 10 位）。密码只从本机终端读取，不经过命令行参数，
也不会写入日志。已经存在管理员时该命令直接跳过，不会覆盖已有账号。

需要脚本化初始化时（密码经标准输入传入，同样不落命令行与日志）：

```bash
printf '%s' "$ADMIN_PASSWORD" | docker compose run -T --rm api \
  python -m app.cli bootstrap --username admin --display-name 平台管理员 --password-stdin
```

## 三、建项目、环境与用例

打开前端地址，用上一步创建的管理员登录，然后：

1. 工作空间里创建项目。项目决定用例、环境与执行池的归属。工作空间还没有项目时创建表单
   直接显示；已经有项目之后用页头的「＋新建项目」展开同一份表单。
2. 在左侧「环境」中创建测试环境，地址填受控目标。本机默认提供两个受控目标服务
   `http://echo:8080` 与 `http://echo-alt:8080`，用于真实验收。
3. 点「＋新建用例」，填请求方法、路径与断言；出参断言在字段旁按可读路径配置，
   例如 `data.id`、`items[0].price`。也可以用「导入 cURL」把一条现成命令解析进编辑器，
   导入不会发送请求。
4. 「保存并发布」把当前草稿固化为一个版本。

### 请求里的变量如何渲染

变量写法是 `{{变量名}}`，取值来自项目普通变量与执行环境普通变量（同名时环境级优先），
在**发送前**按本次执行的冻结输入解析。未定义的变量在发出请求前直接失败：不会静默替换，
也不会把 `{{...}}` 当字面量发出去。保存和导入都不发送请求。

**纯文本正文、路径、查询参数、请求头**是文本协议，按字面文本替换，不存在类型：
数字变量 `shared=1` 在这几处写成 `1`。

**JSON 正文**先按无损 JSON 解析原文，再逐字段绑定，最后按 JSON 规则写回：

- 占位要写在 JSON 字符串的引号内：`{"score":"{{shared}}"}`。写成 `{"score":{{shared}}}`
  在保存时就会被拒绝，错误信息会给出可照抄的写法。
- 某个字符串**恰好只有一个占位**时，按变量自身的类型写入：数字变量写成不带引号的数字，
  布尔写成 `true`／`false`，null 写成 `null`，JSON 对象／数组变量展开成结构，字符串变量
  写成字符串。
- 占位嵌在更长文本里（`"pre{{n}}post"`）时按字符串写入，类型不随取值改变。
- 数字按十进制原文写回，不经过二进制浮点：`9007199254740993` 逐位不变；科学计数法
  变量 `1E+2` 写成等值的合法 JSON 数字 `100`。
- 取值里的引号与反斜线按 JSON 规则转义，结果仍是可解析的 JSON。
- 对象键也支持变量；两个键渲染成同一个键时会报错，不会静默覆盖。
- 正文里不含变量时按原文逐字节发出，不重排、不折叠重复键。

可照抄的例子（项目普通变量：`shared` 数字 1、`big` 数字 9007199254740993、
`flag` 布尔 true、`who` 字符串 张三）：

| 正文 | 目标收到 |
| --- | --- |
| `{"score":"{{shared}}","label":"abc"}` | `{"score":1,"label":"abc"}` |
| `{"id":"{{big}}"}` | `{"id":9007199254740993}` |
| `{"on":"{{flag}}"}` | `{"on":true}` |
| `{"user":"{{who}}"}` | `{"user":"张三"}` |
| `{"text":"pre{{shared}}post"}` | `{"text":"pre1post"}` |

**表单正文**（`application/x-www-form-urlencoded`）先按表单协议解析成有序、可重复的
字段列表，再逐字段替换，最后按表单协议编码：

- 取值里的 `&`、`=`、`+`、空格、中文都不会改变字段边界。变量 `value=a&b=c` 配 `q={{value}}`
  发出后，目标按表单协议解码得到的是**一个** `q` 字段，取值完整为 `a&b=c`。
- 重复字段的顺序与个数原样保留（`a=1&a=2&b={{value}}&a=3` 解码后仍是四项）。
- 正文里不含变量时按原文发出，连 `a=b&c` 这种省略等号的写法也保留。
- 变量名写成 `{{a+b}}` 会被拒绝：表单解码会把 `+` 变成空格，解析后已不是同一个引用，
  按字面量发出去等于发了一份没写过的正文。

JSON 正文里的入参断言读的是**最终准备后的正文**（含类型），所以
`{"score":"{{shared}}"}` 上的 `range 0/100` 按数字判断，不会把数字当字符串判 `type_error`。

## 四、把执行池授权给执行进程

用例执行由独立执行进程（worker）完成，它只领取被显式授权的执行池。**未配置
`WORKER_POOL_IDS` 时 worker 会明确报错退出**，不会静默空转，也不会领取任意池。
创建项目时系统会为项目建立默认执行池，先把它列出来：

```bash
make pools
```

输出形如：

```
执行池（把 id 配置到 worker 的 WORKER_POOL_IDS，多个用逗号分隔）：
  <pool-id>  默认执行池  状态=active  项目=示例项目（<project-id>）
```

把 id 填进 `.env`（多个用逗号分隔）：

```
WORKER_POOL_IDS=<pool-id>
```

worker 允许访问的目标由执行池的**目标白名单**决定，白名单可以在页面上的
「执行池与目标白名单」里维护，不需要改数据库。白名单是出网来源的唯一入口：必须先加
白名单，再执行用例；保存白名单只改配置，不会访问任何目标。

白名单不是唯一边界。环回、未指定地址、链路本地／云元数据，以及平台自身的基础设施
（管理 API、数据库、前端、执行器宿主机入口，含 `api`／`db`／`host.docker.internal`
及其当前解析到的地址）一律不能作为被测目标，填进白名单也不会被放行——这条判断在创建
运行和真正发送前各做一次，改写写法（`::ffff:127.0.0.1`）或改用 IP 直连都绕不过。

平台自身的禁区由可信部署配置定义：基线名单已覆盖当前 Compose，需要追加平台所在网段或
额外主机名时改 `.env` 里的 `PLATFORM_FORBIDDEN_HOSTS`／`PLATFORM_FORBIDDEN_ADDRESSES`
（只能追加，不能删减基线）。公司内网的测试目标属于普通私网，显式写进白名单后照常可用。

这两项是**静态**名单：名字写错也照旧拒绝，当前部署没在用的兼容别名同样在内。与之配套的
`PLATFORM_REQUIRED_HOSTS` 声明本次部署**实际启用**、必须完整确认地址的来源。每次发送前
这些名字必须全部解析成功，否则这次发送被拒绝——解析失败时拼不出完整的禁区，而“解析不了
就跳过”会让指向同一台主机的别名合法绕过去。管理 API、数据库（`api`／`db`）与**容器到
宿主机的入口**（`host.docker.internal`）由代码基线无条件要求，部署配置删减不了；
**执行器**（`worker`）是部署可选的服务，只有运行它的部署才把它写进来（见下一节）。
其它平台的兼容别名不必列，缺了也不会破坏干净安装。它由部署配置决定，用例、运行请求与项目白名单都
改不动，进程也不会为了“确认来源”向任何地址发请求。两类失败分得很清：**配置写错**（写成 URL、带路径或“名字:端口”）在创建运行时就按配置
错误拒绝，运行不落库；**必需来源解析不出来**属于发送前的地址复核，运行会按策略失败并在错误里点名
确认不了的主机，一个请求都不会发出去。

宿主入口为什么必须在基线里，以及模板怎么提供它：宿主既跑着平台本体、又常常是公司内网的
入口，只把它当“可选别名”时，指向它的域名和直接写宿主 IP 两条路径都只剩主机名检查，换个
域名就绕过去了。模板因此无条件提供这条入口（`compose.yaml` 的
`extra_hosts: host.docker.internal:host-gateway`；`host-gateway` 在 Linux 与 Docker Desktop
上都解析到宿主自己），不需要你去找宿主 IP。改用别的部署方式时，要么提供等价的宿主入口，
要么用 `PLATFORM_FORBIDDEN_ADDRESSES` 显式声明宿主的地址／网段；两者都没有时发送会被拒绝，
而不是悄悄少一层保护。这条模板契约由 `make check-template`（在 `make check` 里）直接检查
展开后的 Compose 配置：Docker Desktop 会自己注入 `host.docker.internal` 的解析，删掉
`extra_hosts` 在开发机上照样能解析，只有这一层能在任何平台上发现模板缺了它。

## 五、启动执行进程并真实执行

`make up` **不会**启动 worker：它在 Compose 的 `worker` profile 里，避免在还没授权时
就跑起来；验收也不能依赖这一步隐含的手工操作，所以用显式命令启动。它同时是**部署可选**的
服务，所以不是必需来源的基线——启动之前先把它的名字声明进 `.env`（服务名就是 `worker`）：

```
PLATFORM_REQUIRED_HOSTS=api,db,web,worker
```

执行器进程启动时会自查这条声明（比对 `WORKER_HOST`，Compose 里就是服务名 `worker`），缺了
直接报错退出并说明改法：否则一台正在运行的执行器既不在必需来源里，也没有任何地方会发现它
没被算进禁区。启动时同时确认**宿主入口此刻解析得到**（同一份地址层禁区），确认不了同样拒绝
启动——宁可起不来，也不要一台持续空转、却把宿主地址敞开的执行器。运行期间 `worker` 必须
可解析（容器在跑就成立）；`make worker-down` 之后要么接受发送在地址复核阶段被拒，要么把
这一项去掉。

检查流程不依赖执行器：`make check` 里的集成测试用与 worker 完全同一份 `claim_job`／
`execute_claim` 在进程内真实执行，干净克隆只需要 `make up` + `make check`。

```bash
make worker        # 等价于 docker compose --profile worker up -d worker
make worker-logs   # 跟随日志
make worker-restart # 改了 apps/api/app 下的代码之后重启（见下）
make worker-down   # 停止
```

worker 是常驻进程，不像管理 API 那样带 `--reload`：改了 `apps/api/app` 下的源码后，
API 会热更新，worker 仍跑改动前的模块，页面上的执行结果因此与源码对不上——新加的
校验看上去像是没生效。验证执行链路的改动前先重启它：

```bash
make worker-restart
```

它只重启进程，**不重建容器**：改了 `.env`（包括上面的 `PLATFORM_REQUIRED_HOSTS` 声明）后
环境变量仍是旧值，执行器会按旧配置自查并有可能直接拒绝启动——这时用 `make worker`
（`up -d`，按新配置重建容器）而不是 `make worker-restart`。改 `apps/api/app` 下的源码不受
此限，重启进程即可加载。

回到页面，在「执行与历史」里点「保存并执行」：提交固定已发布版本，由 worker 领取后
真实发起请求，结果与断言逐条回填。若目标不在白名单内，运行会明确失败并给出原因，
不会静默通过。

凭证用途授权按签发时生效的项目／环境普通变量冻结输入。改动生效变量（环境级变量优先
于项目级同名变量）之后，原授权会被以 `credential_inputs_changed` 拒绝且不发出任何
请求，需要在「人工凭证」里重新签发，再执行。

## 六、验证与停止

```bash
make check
make stop
```

`make check` 包括前端类型检查、组件行为测试与生产构建，后端静态检查与纯行为测试，
数据库表列中文注释校验，真实 PostgreSQL 上的集成测试（RLS、角色隔离、工项领取与
结构契约），以及前后端联通性检查。

源码修改和依赖变更对应不同的更新机制。首次构建需要访问镜像仓库与软件包源；
多个工作目录默认使用不同的 Compose 项目名和独立数据卷。

## 约定

- `.env.example` 只提供无敏感信息的通用字段。真实 `.env`、数据库口令、加密主密钥与
  其他本机专属配置不得提交。
- 秘密（口令、令牌）只能通过页面的「人工凭证」登记，保存后不再显示明文；普通变量
  不收秘密，服务端会直接拒绝。
- 本阶段不启用生产环境执行，创建生产环境会被服务端拒绝。
